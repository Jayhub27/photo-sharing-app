# Mobile support

The goal: photographers and guests can use Take the shot from any phone browser,
and regulars can install it like an app. Two clients exist — the responsive web
app (now an installable PWA) and the optional Expo app.

## What was researched

**PWA on iOS (2026 state)** — Safari has no `beforeinstallprompt`. Installation is
manual via Share → *Add to Home Screen*; since iOS 16.4 any browser can install,
and iOS 26 opens home-screen sites as web apps by default. Service workers and
Cache API work; background sync and background fetch do not. Practical rules:

- Ship a manifest with `display: standalone`, 192/512 px icons plus a maskable
  icon, `apple-touch-icon` and `apple-mobile-web-app-*` meta tags.
- On iOS show instructions, on Chromium capture `beforeinstallprompt` and show a
  button; never rely on the automatic prompt.
- Detect standalone with `display-mode: standalone` *and* `navigator.standalone`.

**Mobile uploads** — the failure modes are memory, HEIC and flaky networks:

- Decoding a 12 MP photo costs ~48 MB of RGBA; decoding a batch in parallel can
  kill a mid-range phone's tab. Decode one at a time, `bitmap.close()` early.
- iOS may transcode HEIC to JPEG automatically when the picker does not list
  `image/heic`. `createImageBitmap` cannot decode HEIC outside iOS, so resizing
  must be optional: on failure, upload the original.
- `createImageBitmap(file, { imageOrientation: 'from-image' })` applies EXIF
  rotation, otherwise portrait photos arrive sideways.
- Downscale to ~2048 px / JPEG q0.85 before upload: a 4-6 MB camera original
  becomes ~300-500 KB, which is the difference between a 25 second upload that
  can die on a cell handoff and a reliable one.
- Upload files sequentially with per-file progress and continue after failures.
  Chunked/resumable transfer matters above ~20 MB; photos rarely reach that.

**Native (Expo)** — the existing app targets Expo SDK 51. Upgrading the SDK
blind, without a device in the loop, risks breaking `expo-camera` and friends, so
the app stays on SDK 51 and instead became a complete, verified client: it now
mounts (the entry point was only `export default App`, so nothing registered a
root component and the app rendered blank), takes photos with the camera, and
points at any server at runtime instead of a hardcoded LAN IP.

## What the code does now

### Web: installable PWA

- `server/public/manifest.webmanifest` — standalone display, theme colors,
  maskable icon, shortcuts.
- `server/public/sw.js` — versioned cache for the app shell (`/offline.html`,
  icons). Network-first for navigations with an offline fallback; **API requests
  are never cached** so private photos cannot leak between sessions.
- `server/public/icons/*` — 192/512/maskable/apple-touch icons, generated by
  `scripts/generate-icons.mjs` from `server/public/icons/icon.svg`.
- `server/src/ui.ts` — manifest/meta tags, service worker registration, update
  prompt, Chromium install button, and an iOS "Add to Home Screen" hint shown
  after a couple of visits instead of on first load.
- Safe areas: `viewport-fit=cover`, `env(safe-area-inset-*)` for the top bar,
  bottom bars, toasts, lightbox controls. `min-height: 100dvh` fallbacks for iOS
  toolbars.

### Web: mobile upload pipeline

`server/src/page-collection.ts`:

- Two pickers: **Choose photos** (library, `multiple`) and **Take photo**
  (`capture="environment"`).
- Client-side downscale (max 2048 px, JPEG 0.85) before upload, one image at a
  time, with the original file as a fallback when decoding is unsupported.
- Sequential uploads over XHR with a real progress bar and "photo N of M" text;
  per-file errors are reported without aborting the rest of the batch.

### Expo app

- `app/index.ts` calls `registerRootComponent(App)`. Without it the app never
  mounted on native or web.
- `app/src/api.ts` resolves the API base at runtime: `EXPO_PUBLIC_API_BASE`,
  then a user-configured server URL stored on device, then `localhost` on web.
  If none is set, requests fail with a clear message instead of hitting a
  hardcoded IP.
- Runtime server URL field on the login screen, stored with the same secure
  storage used for the session.
- Uploads: library picker (`allowsMultipleSelection`) plus a **Camera** button
  using `launchCameraAsync`; sequential uploads with an on-screen
  "Uploading N/M" progress bar.
- On web the picker returns a `blob:` URL, so `appendPhoto()` fetches it and
  appends a real `File`; on native it appends the `{ uri, name, type }` object
  that React Native expects. This makes the same upload path work in both.
- `app/assets/icon.png` and `adaptive-icon.png` (generated from the same SVG as
  the PWA icons) so `expo prebuild` produces a branded APK/icon.
- `app/.env.example` documents the API base variable.

## Verification checklist

1. `npm run build --workspace server` and `npx tsc --noEmit -p app/tsconfig.json`.
2. Open `http://localhost:3000` at 390x844 in Chrome DevTools → Application →
   Manifest shows no errors, service worker activates, offline reload serves the
   offline page.
3. Install from Chrome (Android/desktop): the install button appears in the UI.
4. On iOS Safari: Share → Add to Home Screen, then verify standalone launch and
   that the hint is hidden once installed.
5. On a phone: take a photo in a collection; the progress bar advances per file
   and the uploaded image is correctly rotated.

## Future work

- Authenticated download/save of purchased originals on device
  (`expo-file-system` + `expo-media-library`/`expo-sharing`); the web app already
  has ZIP and single-file downloads.
- Chunked/resumable uploads for very large batches and videos.
- Expo SDK upgrade (52+) with on-device testing, and shared code between the web
  and native upload pipelines.
- Web push notifications for new photos in a shared collection (iOS 16.4+).
